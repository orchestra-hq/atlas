# Open questions

Decisions that need the project owner's call (or at least sign-off). When a question is resolved, the outcome is recorded in the doc (or ADR) that owns it and the question is deleted here — git history keeps the trail; this file only ever lists what is actually open.

## Hard enforcement of `tool_choice` forcing (phase 4)

Atlas translates Anthropic `tool_choice` correctly — `auto → auto`, `any → required`, `{type:tool,name} → {type:function,function:{name}}`, `none → none` — and forwards it to the engine ([api-surface.md](api-surface.md), `internal/engines/llamacpp`). But the pinned llama.cpp build (`b9611`) with the Qwen2.5 chat template treats forcing as **advisory**: it selects the named/appropriate tool when the prompt motivates a call, yet will emit plain text (no tool call) when the prompt runs contrary to the forced choice. So `any` / `{tool}` do not _guarantee_ a tool call the way the Anthropic API does.

True forcing would require the gateway to constrain decoding (e.g. supply a GBNF/JSON-schema grammar that mandates a tool call) rather than relying on the engine to honor `tool_choice` — which edges toward reimplementing engine behavior (ADR-0001). **Open:** do we (a) accept best-effort forcing in M0 and document it, (b) add gateway-side grammar enforcement, or (c) gate it on an engine-version bump once a build enforces `tool_choice:required`? Until decided, the G3 suite asserts tool selection on prompt-motivated tasks (the conformance philosophy) rather than forcing against a contrary prompt.

## Reasoning control is model-convention-specific (phase 5)

Atlas maps engine reasoning output to Anthropic `thinking` blocks (ADR-0005) and toggles reasoning per request via the engine's chat-template kwarg `enable_thinking` — the convention hybrid-thinking models (Qwen3, …) expose through llama-server's `--jinja` templating (`internal/engines/llamacpp`, `thinkingKwargs`). This is a **convention, not a standard**: a reasoning model that gates thinking differently (a system-prompt token, a distinct kwarg name, always-on with no off switch) would not respond to `enable_thinking`, so a client that did not request thinking could still get reasoning (which Atlas then drops from the response, wasting tokens but staying correct). `budget_tokens` is **accepted and ignored** on llama.cpp: there is no reasoning-budget knob, and ADR-0005 forbids enforcing budgets by truncation, so it stays advisory.

Both are clean once a per-model reasoning-parser/config registry exists (ADR-0005 consequence). Phase 9 added the catalog, which **records** per-model config (a `reasoning` flag and per-engine `engine_args` carrying the vLLM tool/reasoning parser flags).

**Partially resolved (M2 phase 4b):** the catalog `reasoning` flag is now **consumed** — it gates the `enable_thinking` chat-template kwarg. A reasoning model gets the kwarg (set from request intent); a **non-reasoning model omits it entirely**, so Atlas no longer injects a template var the model does not use (previously sent always, relying on it being a harmless no-op). The flag threads `worker.Config` → `openaichat.Client`, gated in `ThinkingKwargs`, so it applies uniformly across llama.cpp and the OpenAI-compatible engines (vLLM/MLX/SGLang). The G4 suite's structural assertions (thinking present/absent, deltas stream, graceful no-op) continue to hold.

**Still open:** a richer per-model reasoning _style_ for models that gate thinking differently than the Qwen3 `enable_thinking` convention — a distinct kwarg name, a system-prompt token, or always-on with no off switch. The current `reasoning: bool` cannot express those; a catalog with such a model would need a reasoning-style field (and the matching adapter logic). Deferred until such a model enters the shipped catalog. `budget_tokens` remains advisory (ADR-0005 forbids truncation).

## The capable/GPU acceptance tier gates M0 "done" (phases 8, 11)

Two parts of the M0 acceptance run need a model and host beyond the CPU PR tier, and they share one blocker — a CUDA runner that does not exist yet. Until that run is observed, **M0 is not declared done** (the project owner's call):

1. **vLLM, all groups (phase 8).** The vLLM adapter, uv runtime provisioning, and `atlas up --engine vllm` landed in phase 8 (sharing the core⇄OpenAI translation with llama.cpp via `internal/engines/openaichat`; unit-tested), but vLLM does not run on the CPU PR runner. So the per-PR gate stays llama.cpp, and "both engines green" is asserted by construction (shared translation + unit tests), not yet observed end-to-end on vLLM. The pinned `VLLMVersion` (and the Qwen `--tool-call-parser hermes` / `--reasoning-parser qwen3` flags) must be re-validated when that run first executes.

2. **Real Claude Code drop-in, G9 (phase 11).** G9's `agent-sdk` cell — a streamed agent loop driving ≥3 client-side tool calls through Atlas — runs and gates per-PR on the small llama.cpp model (the tool is forced each turn, so the loop is deterministic). Its `claude-code` cell — the real `claude` binary editing+verifying a file via `ANTHROPIC_BASE_URL` — is **opt-in** (`CONF_CLAUDE_CODE_SMOKE=1`): empirically the 1.5B catalog model drives Claude Code only intermittently (it emits the edit but does not reliably complete the agentic loop within the turn budget), so as a per-PR gate it would flake. Reliable Claude Code drop-in needs a capable model. (The smoke did surface a real drop-in bug that is now fixed regardless of model size: Claude Code sends `thinking.type: "adaptive"`, which Atlas rejected with a 400 — see [api-surface.md](api-surface.md) and ADR-0005; the gateway now accepts it.)

The harness is engine- and client-agnostic: the same `run.py` runs `--engine vllm` against a vLLM-backed `atlas up`, and `CONF_CLAUDE_CODE_SMOKE=1` (with `CLAUDE_CODE_MAX_OUTPUT_TOKENS` sized to the model's context) enables the real Claude Code cell.

**Related M2 phase 3 runner gaps (G17).** Engine breadth adds two more nightly cells that each need a runner the CPU PR tier does not provide, mirroring the blocker above:

- **SGLang (phase 3b)** is a second NVIDIA-GPU server, so its G17 cell shares the **same CUDA runner** the vLLM acceptance run waits on — once that runner exists, both vLLM and SGLang assert nightly on it. As with vLLM, the pinned `SGLangVersion` and the catalog's SGLang `--tool-call-parser` / `--reasoning-parser` flags are unit-validated against the server's source but must be re-validated end-to-end on that first GPU run.
- **MLX (phase 3a)** runs only on **Apple Silicon** (`darwin/arm64`, Metal), so its G17 cell needs an **Apple-Silicon CI runner** that does not exist yet (GitHub-hosted `macos-14`+ arm runners or a self-hosted Mac). Until one is wired up, MLX is exercised by the per-PR unit/fake-runner tests (adapter translation, the `max_tokens:1` count-tokens probe, provisioning orchestration) and by local Mac runs, but the real G1–G8+G10 suite on MLX is not gated. Flagged here, not silently shipped.

**Related M2 phase 4c gap (G18).** The agent-capability matrix is generated by [`conformance/capability_matrix.py`](../conformance/README.md), which aggregates the per-(engine, model) `matrix.json` runs into the published "works for agents" matrix. The generator and its verdict logic are unit-tested on the CPU PR tier, and the per-PR conformance job runs it on the single llama.cpp cell it produces — but the **full** matrix (every catalog model × every engine that can serve it) is only as complete as the runs feeding it, which require the same dormant CUDA + Apple-Silicon runners as G17. So a representative published matrix is gated on those runners; until then the tool is proven end-to-end on one real cell. Catalog expansion (the larger gguf tiers) feeds more rows as each model's quant digest is pinned and verified — the standing pin-on-verify activity above.

**Plan (decided):** this is now the **M0.5 "Release & prove"** milestone ([roadmap.md](roadmap.md), [ADR-0006](decisions/0006-packaging-and-deployment.md)). The machinery is in place: the provider-agnostic [`scripts/acceptance.sh`](../scripts/acceptance.sh) runs the full gate + `CONF_CLAUDE_CODE_SMOKE=1` on both engines, the nightly workflow ([`examples/acceptance/`](../examples/acceptance/README.md)) provisions an on-demand GPU box via `machulav/ec2-github-runner` (SkyPilot was dropped here — its Ray bootstrap clashed with the recent-driver AMI vLLM needs, and spot preemption kept killing runs; see ADR-0006 update). A green run flips M0 to done. Whether to add the dedicated **Claude Agent SDK package** (`claude-agent-sdk`, model-initiated custom-tool loop) as a third capable-tier cell stays open — the small model emits its MCP tool calls as prose, so the per-PR `agent-sdk` cell uses the forced Anthropic-SDK loop instead; the dedicated-package run belongs in this same acceptance pass.

**First GPU run executed 2026-06-22** (manual dispatch, `g6.xlarge` / L4 24 GB, eu-west-2). The infra (OIDC, IAM, region, spot acquisition) all worked; the acceptance run itself was red, surfacing real drop-in issues exactly as this section anticipated:

- **vLLM exited 1 at engine start** — its raw `--tool-call-parser hermes` flag was passed without the required `--enable-auto-tool-choice`. Fix: the acceptance run now serves a **catalog** model (`qwen3-8b`), whose `engine_args` carry the full, correct flag set.
- **Qwen3 leaked `<think>` blocks into non-reasoning replies**, emptying the answer within the token budget → mass G1/G2/G8 failures plus the explicit G4 assertion. Root cause: serving the hybrid model via a raw spec skips the catalog `reasoning` flag that gates `enable_thinking` (the documented raw-hybrid gap in [follow-ups.md](follow-ups.md)). Fix: serve via catalog (`qwen3-8b` / `qwen3-8b-gguf`, both `reasoning: true`).
- **`GET /v1/models/{id}` 404'd (G5)** for the raw served id `Qwen/Qwen3-8B` — the embedded slash split the URL path. Cataloging gives a slug served id (`qwen3-8b`), which routes cleanly.
- **The nightly reported green despite the red acceptance run** — `sky launch --down` returned 0 even on job failure. Resolved by the move to machulav: acceptance now runs as a native workflow job, so its exit code _is_ the gate.

Subsequent runs (2026-06-22) confirmed the catalog fixes — llama.cpp went to **45 passed, 2 failed**, the two stragglers being G4's non-reasoning-graceful (needs a genuinely non-reasoning model — added `qwen2.5-7b-instruct-gguf` for sonnet/haiku, `qwen3-8b-gguf` for opus) and the Claude Code smoke timing out (timeout raised, capable non-reasoning model now drives it). Two infra blockers also surfaced and were addressed: **vLLM 0.23.0 needs NVIDIA driver ≥580 (CUDA 13)** vs the stock AMI's ~535 — fixed by provisioning a recent-driver AMI directly (the reason SkyPilot was dropped, since that AMI clashes with SkyPilot's Ray); and **spot preemption** repeatedly killed mid-run — fixed by running **on-demand**.

**Both engines now serve on the GPU box (2026-06-23)** after clearing a long stack of host issues (disk size, 16→32 GB RAM for weight staging, vLLM `--enforce-eager` for the 24 GB card, a raised engine ready-timeout for the cold download+load, and disabling vLLM's FlashInfer sampler whose JIT needs a `ninja`/CUDA toolchain the runner lacks — `VLLM_USE_FLASHINFER_SAMPLER=0`). Standing results: **llama.cpp 46/46** (CPU track, capable model — full API conformance; the Claude Code smoke is a GPU-tier cell, skipped here), **vLLM 43/47** (real Claude Code drop-in passes; see below). The remaining vLLM failures:

- **4× G4 thinking** — an **upstream vLLM bug**, not Atlas. vLLM's `qwen3` reasoning parser mishandles _budget-truncated_ reasoning (when `max_tokens` is hit before `</think>`): the output lands in neither `reasoning_content` (where Atlas reads it) nor usable `content`, so Atlas emits empty blocks. The conformance tests use `max_tokens=128`, which truncates Qwen3 mid-think. Atlas's mapping is correct — the _same model_ passes all four G4 tests on llama.cpp (llama-server surfaces partial `reasoning_content` incrementally). See [vLLM #35221](https://github.com/vllm-project/vllm/issues/35221), [#38894](https://github.com/vllm-project/vllm/issues/38894), [#40816](https://github.com/vllm-project/vllm/issues/40816). Treated as a documented vLLM limitation pending an upstream fix. **⚠️ Revised 2026-06-24 — see the correction below: vLLM #35221 is closed and its fix shipped in the pinned 0.23.0, and a G4 thinking cell now fails on llama.cpp too, so this "upstream-only, proven correct by llama.cpp" framing no longer holds.**
- **1× Claude Code smoke** — was `exit=1` ("Prompt is too long"): Claude Code's system prompt + tool definitions are ~24k tokens, but vLLM was launched with `--max-model-len 8192`. **Fixed (2026-06-23)** by raising it to `32768` (fits one sequence in the ~34k-token KV cache): **the real Claude Code drop-in now passes on vLLM** — Claude Code edited + verified a file against a self-hosted Qwen3-8B via `ANTHROPIC_BASE_URL`. vLLM is now **43/47**, the only failures being the four upstream-bug G4 thinking tests above.

The literal M0 demo — real Claude Code drop-in on a capable model on your own hardware — is therefore **proven on vLLM**. The CPU track confirmed the smoke cannot complete on CPU even on a fast 16-vCPU box (the 7B is too slow), so it is a GPU/capable-tier cell, skipped on the CPU track. Remaining before M0 is formally declared done: a green-on-both view, which today means treating the four vLLM G4 thinking cells as a documented upstream vLLM limitation (Atlas's mapping is correct, proven by llama.cpp passing them). **⚠️ Withdrawn 2026-06-24 — this plan rested on llama.cpp proving the mapping correct, which no longer holds; see the correction below.**

**Nightly topology (decided 2026-06-23):** split into two parallel tracks — a **GPU box (g6.2xlarge)** for vLLM and a **compute-optimised CPU box (c7i.4xlarge)** for llama.cpp. llama.cpp ships no Linux CUDA prebuilt (only Windows CUDA / Linux Vulkan-ROCm-SYCL), so per ADR-0001 it stays the CPU engine and GPU is vLLM's lane; the faster CPU box is also the best shot at the llama.cpp Claude Code smoke completing. Still open: the vLLM Claude Code `exit=1`, and whether the c7i CPU box drives the Claude Code smoke to green.

**Correction & new findings (2026-06-24).** The conformance harness was masking a real failure, and the vLLM-G4 framing above needs revision. Decision (the project owner's): **fix all of the below before M0 is declared done — do not xfail / mask.**

- **Conformance-harness bug fixed ([PR #73](https://github.com/orchestra-hq/atlas/pull/73)).** `conformance/run.py` passed a _relative_ `--outputFile` to vitest, which vitest resolved against its own cwd (`conformance/ts/`, writing `conformance/ts/results/…`) while the harness checked the path against `conformance/`'s cwd — so vitest's results file _was_ written but never found, aborting otherwise-green runs with "vitest produced no results file" _before the gate ran_. ## Catalog data the gateway records but does not yet apply (phase 9)

The starter catalog (`/catalog`) carries fields the build wires through to **storage**; M2 phase 4 applies them to **request handling**:

1. **Per-model sampling defaults** (`sampling.temperature` / `top_p`) — recorded per entry (wrong defaults visibly degrade tool calling, [model-catalog-m0.md](research/model-catalog-m0.md) finding 3). **Resolved (M2 phase 4a):** the worker applies them at its `Execute`/`ExecuteStream` choke point — a request that omits the field picks up the catalog value, an explicit value always wins, and a raw path/spec (no entry) leaves the field unset for the engine to default. Threaded via `worker.Config`, so both local (`atlas up`) and fleet workers get it with no wire/gateway change.
2. **Per-model reasoning config** (`reasoning`) — **Resolved (M2 phase 4b):** the flag gates the `enable_thinking` chat-template kwarg (a non-reasoning model omits it). Threaded via `worker.Config` → `openaichat.Client`, applied uniformly across engines. See the reasoning-convention question above for the residual open part (richer reasoning _styles_).
3. **Tier metadata** (`tier: haiku|sonnet|opus`) — recorded but does not auto-generate the `claude-*` aliases; `atlas up --alias` is still explicit. Still open: leave to the operator via `--alias`, or auto-derive?

Also parked here: the larger gguf tiers (the research-doc 9B–35B models) are not in the shipped catalog because their exact quant digests are not yet pinned — add them as each is verified at build time (pinning is required: `internal/catalog` rejects a gguf entry without a 64-hex sha256). M2 phase 4c expands the catalog as digests are pinned.

## Readiness does not re-probe a live engine (phase 10)

`/readyz` returns 200 once a model is registered, and in single-node mode a model is registered only after its worker's `Start` confirms the engine reported healthy — so at startup "ready" genuinely means "a model can answer". It is **not** a live probe: if an engine subprocess dies _after_ registration, `/readyz` keeps returning 200 (the next request surfaces the failure as a 529). For M0's single-node hero path this is acceptable; a periodic worker health re-probe feeding readiness is an M1 concern, alongside the remote-worker hub. Stated as an assumption rather than silently shipped.

## Seeding a chosen API key for non-interactive deploys (phase 5)

[ADR-0008](decisions/0008-control-plane-persistence-and-api-keys.md) removed the shared `--api-key` secret: the control plane mints a default key on first run and prints it, and `atlas keys create` mints more. This is clean for interactive use, but non-interactive deploys (Docker, the SkyPilot recipe, k8s, anything driven from a secrets manager) can no longer **inject a known key** — they must scrape it from the process logs (`docker logs` / `sky logs`) after boot. The recipes in `examples/serve` and `docs/docker.md` do exactly that today.

**Open:** add a first-boot seed path so an operator can supply the exact secret out of band — e.g. an `ATLAS_API_KEY` env (or `--seed-key`) that, **only when the store is empty**, creates a key with that value instead of a random one. The tension is convenience vs. reintroducing a shared-secret-shaped env var that ADR-0008 deliberately retired; mitigations would be to seed only on an empty store and to document it as a bootstrap convenience, not an auth mechanism. Flagged during phase 5a; nothing depends on it (the log-scrape path works), so it is deferred rather than built.

## Resolved

Auth for the `/admin/*` control surface (phase 5) — settled in [ADR-0008](decisions/0008-control-plane-persistence-and-api-keys.md): gate `/admin/*` with an **admin-scoped API key** (option (a)), reusing the same key store and middleware as the client `/v1/*` surface rather than a separate token or loopback listener. The admin CLI clients send the key via flag or `ATLAS_API_KEY`. G12 grows an admin-auth case. Until phase 5 lands, the surface stays unauthenticated and M1's threat model assumes the server port is reachable only by trusted operators and workers.

How workers get engine runtimes — settled: M0 ships managed runtimes only (downloaded prebuilt llama.cpp binaries, a `uv`-managed vLLM venv), with the container path arriving at M1 behind the same provisioner interface. Recorded in [m0-build-plan.md](m0-build-plan.md#engine-runtime-provisioning) and implemented for llama.cpp in phase 2.
