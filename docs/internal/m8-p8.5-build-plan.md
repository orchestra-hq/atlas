# M8 Phase 5 (P8.5) — conformance gate + acceptance

> Build-ready breakdown of **M8 Phase 5** from [m8-build-plan.md](m8-build-plan.md) ("conformance + acceptance"), under the ratified [ADR-0015](decisions/0015-bring-any-model-auto-configuration.md). Phases 1–4 built the read-only metadata→`Capabilities` layer ([P8.1](m8-p8.1-build-plan.md)), the family map + metadata-driven serving ([P8.2](m8-p8.2-build-plan.md)), the load/fit gate that fails fast before any download ([P8.3](m8-p8.3-build-plan.md)), and the warn-and-serve middle case + `--require-verified` + contributor doc ([P8.4](m8-p8.4-build-plan.md)). The auto-config path now exists end to end — but its **only** end-to-end proof today is Go unit/integration tests against httptest HF endpoints and fakes. No conformance group proves that a model auto-configured from its own metadata, with **no catalog row anyone wrote**, actually serves an **agent-grade** endpoint (tool calls, streaming, reasoning) on a real engine. Phase 5 closes that gap — the M8-done gate — and reconciles the public prose that still calls bring-your-own "best-effort."

## Goal

A new conformance group **G23** brings up `atlas up --model <known-family-HF-repo>` for a repo that is **not in the starter catalog**, asserts that resolution **auto-configured** it from its family metadata (the `Auto-configured … family` startup line — i.e. it took the `modelmeta.Classify` path, not the bare passthrough), and then runs the existing **agent-critical conformance gates** (messages, streaming, tool loop, thinking, the streamed ≥3-call agent-SDK loop) against that auto-configured endpoint — proving the metadata-driven serving plan is agent-grade, on a real llama.cpp deployment, per-PR. This mirrors how M3's `Conformance (M3)` job ([scripts/conformance-m3.sh](../../scripts/conformance-m3.sh)) gates G19–G22 on a real CPU deployment. With G23 green, the M8 acceptance criterion — "a newcomer serves an agent-grade endpoint from one `atlas up --model <repo>` with no catalog entry written by anyone" — is proven by the suite. Phase 5 also reconciles the two user-facing surfaces that still promise "best-effort" raw weights ([guides/models.md](../../website/src/content/docs/guides/models.md), [launch-post.md](../../docs/launch-post.md)) so they promise auto-config + the honest three-way verdict, and writes the M8 acceptance report.

## What already exists (seams this phase extends)

- **The conformance harness** — [conformance/run.py](../../conformance/run.py) drives the G-groups against an external Atlas via `--base-url`, with `--model` / `--reasoning-model` / `--engine` / `--require G1,G2,…`. The agent-critical groups are **G3** (tool loop) and **G9** (the streamed ≥3-call agent-SDK loop), per the G18 agent-readiness verdict ([conformance-suite.md](conformance-suite.md):139). The harness is engine- and model-agnostic — it talks only to the endpoint — so pointing it at an auto-configured model needs **no harness change**, only a new driver script that boots that model and calls `run.py`.
- **`scripts/conformance-m3.sh` + the `Conformance (M3)` CI job** ([ci.yml](../../.github/workflows/ci.yml):591) — the template for a new per-PR conformance tier: a standalone bash script that builds `atlas`, provisions a key, boots a real llama.cpp deployment, runs assertions, and is wired as one CI job with model-store + runtime caches. G23's script and job are the M8 analogue.
- **The auto-config serving path** — [resolveRaw](../../internal/cli/resolve.go):114: a non-catalog spec is inspected; a **known family** (`modelmeta.Classify`) yields a full plan (parser `engineArgs`, reasoning gating, sampling, context) and prints `Auto-configured %q as the %s family: …` (resolve.go:156). That startup line is G23's machine-checkable signal that auto-config (not the bare passthrough) happened. For llama.cpp the family `engineArgs` are typically template-driven (empty), so the observable auto-config effect on the CPU tier is **classification + reasoning gating + sampling + context** — the parser-flag families (`hermes`/`qwen25`/… on vLLM/SGLang) are the GPU-breadth nightly follow-on, exactly as M3 tiered prefix-cache reuse to nightly.
- **The conformance CI jobs' caching** — [ci.yml](../../.github/workflows/ci.yml):117 caches the content-addressed model store keyed on the catalog; the pinned llama.cpp runtime is cached keyed on `internal/runtime.LlamaCppTag` (`b9611`). G23 serves an HF repo via llama.cpp's `-hf repo:<quant>`, which the **engine** downloads into its own cache at boot — that cache directory is the new thing to cache (keyed on the repo id), so only the first run pays the download.
- **The public "best-effort" prose** — [guides/models.md](../../website/src/content/docs/guides/models.md):34 ("Serving your own weights … raw weights are best-effort") and [launch-post.md](../../docs/launch-post.md):64 ("**bring your own** … serve it best-effort"). Both predate M8 and are the Phase-5 reconciliation targets (the P8.4 plan explicitly deferred this public-prose rewrite to P8.5 to avoid double-touching).
- **The acceptance-report pattern** — [m3-acceptance.md](m3-acceptance.md) is the template for `m8-acceptance.md`: what "done" means, what's proven per-PR, the gate, the criteria, and the GPU-breadth standing follow-on.

## Decisions taken

### Product (owner) — already settled in ADR-0015

- The three-way verdict, the family-map-in-code extension model, and warn-and-serve-by-default are ratified ([ADR-0015](decisions/0015-bring-any-model-auto-configuration.md), 2026-06-28). No new product decision is open in this phase. ### Technical (lead dev)

- **G23 is a real end-to-end shell gate, not a Go test, and lives in `scripts/conformance-m8.sh`** wired as a `Conformance (M8)` CI job — symmetric with `conformance-m3.sh`/`Conformance (M3)`. The Go layer already proves the _resolution logic_ (resolve_test.go, family_test.go, the httptest HF endpoint); the gap M8-done closes is the _real-engine_ proof that an auto-configured plan serves agent-grade, which only a live deployment + the SDK harness can give. The script is CPU-only and runs per-PR.
- **The gate model is a small, known-family GGUF HF repo that is not a catalog name.** Candidate: **`Qwen/Qwen3-0.6B-GGUF`** (Qwen-published official GGUF; GGUF `general.architecture = qwen3` → `normalizeFamily` known family `qwen3`, `Reasoning: true`; ~0.4 GiB at `Q4_K_M`, well within a CPU runner). Choosing a **qwen3** (reasoning) repo means G23 exercises the auto-configured **reasoning gating** end to end via G4, a strictly stronger proof than a non-reasoning model. The repo id `Qwen/Qwen3-0.6B-GGUF` is not a catalog `name` (catalog names are tokens like `qwen3-0.6b`), so `cat.Lookup` misses and it flows through `resolveRaw` — the exact auto-config path under test. **Final repo selected at build time** by confirming `atlas inspect <repo>` classifies it to a known family and it serves + passes the gates on the CPU runner; if the chosen repo is flaky or oversized, fall back to a `Qwen2.5-0.5B`-class known-family GGUF repo (drops G4 reasoning coverage to the graceful-no-op case, keeps G3/G9).
- **G23 asserts auto-config happened, then delegates the agent gates to `run.py`.** The script (a) boots `atlas up --model <repo>` with the tier aliases pointed at the auto-configured served name and captures startup output; (b) asserts the `Auto-configured …` line is present (auto-config, not bare passthrough — the distinguishing claim) **and** that no `warning: serving … as plain chat` line appears (it is a _known_ family); (c) waits for `/readyz`; (d) runs `run.py --base-url … --engine llamacpp --model <served> --reasoning-model <served> --require G1,G2,G3,G4,G9`. G3+G9 are the agent-critical gates; G1/G2/G4 ride along as substrate/streaming/reasoning. A negative control (point the alias at the same repo but assert the gate notices a _missing_ auto-config line) is the script's self-test — see Acceptance.
- **The served name and aliases.** `resolveRaw` derives the served name from the spec via `modelDisplayName` (resolve.go:117). The script reads the served name from `atlas up`'s output (or pins it with the existing `--alias claude-sonnet-4-6=<served>` mechanism the other conformance jobs use) so the harness addresses it. Single served model covers all three tier aliases (as the llama.cpp job already does).
- **Caching the engine's HF download.** llama.cpp's `-hf` download lands in the engine's cache dir under the state dir; cache it in CI keyed on the repo id so only the first PR pays the network cost — the same shape as the existing `conf-store-*` cache. This keeps the per-PR job's HF dependency to a cold-cache first run, no worse than the existing catalog cache-miss path (catalog gguf models also download from huggingface.co URLs).
- **Public-prose rewrite is mechanical and docs-only.** `models.md` and `launch-post.md` change "best-effort" → a one-paragraph statement of the three-way verdict: known family → auto-configured agent-grade serving; loadable-but-unknown family → served as chat with a warning + a one-line contribution pointer (`--require-verified` to refuse); unloadable arch / won't fit → a clean pre-download failure. Cross-link the models guide to the new behavior; the launch post keeps its tone but drops "best-effort." No code, no API.
- **`m8-acceptance.md` is written last, citing the green G23 run**, mirroring `m3-acceptance.md`: it states the per-PR gate (G23 + all prior groups stay green), what the Go tier already proves, and records GPU-engine breadth (parser-flag families on vLLM/SGLang, auto-config across MLX) as the standing **nightly** follow-on, not part of the gate.

## Data model

No DB/migration, no new on-disk artifact, no `Capabilities`/`Verdict`/catalog schema change. G23 is a runtime gate; the docs are prose. The engine's HF cache dir is existing behavior, only newly cache-keyed in CI.

## Sub-phases

### P8.5a — the G23 conformance gate (script + CI job + suite doc)

**Scope.** The substantive engineering slice — prove the auto-config path is agent-grade on a real engine, per-PR:

- New `scripts/conformance-m8.sh` (template: `conformance-m3.sh`): build `atlas`, provision a key, `atlas up --model <known-family-GGUF-repo>` with the tier aliases pointed at the auto-configured served name, capturing startup output. Assert the `Auto-configured … family` line is present and **no** plain-chat warning line is. Wait for `/readyz`. Run `conformance/run.py --base-url … --engine llamacpp --model <served> --reasoning-model <served> --require G1,G2,G3,G4,G9`. Fail loudly with server/engine logs on any miss (mirror `conformance-m3.sh`'s log-dump-on-failure).
- New `Conformance (M8)` job in [ci.yml](../../.github/workflows/ci.yml) (template: the `conformance-m3` job): runs `bash scripts/conformance-m8.sh` on the CPU runner, with a model-store/state cache and the pinned llama.cpp runtime cache, plus a cache of the engine's `-hf` download dir keyed on the repo id. Upload server/engine logs as an artifact (`continue-on-error`, as the other conformance jobs do, so an artifact-quota blip never reds a green gate).
- Document **G23** in [conformance-suite.md](conformance-suite.md) under a new "M8 test groups" section: an auto-configured known-family HF model with no catalog row passes the agent-critical gates (G3 tool use, G9 agent loop) plus G1/G2/G4 substrate, on a real llama.cpp deployment per-PR; GPU-engine breadth (parser-flag families on vLLM/SGLang; auto-config on MLX) is the nightly follow-on. Add the row to the matrix/principles text as the other groups did.

**API.** None — CLI + CI + docs. No HTTP/openapi change, no `make generate`.

**Acceptance (the gate itself is the test — a green `Conformance (M8)` run).**

- `scripts/conformance-m8.sh` run locally (Apple Silicon) and on the CPU runner: `atlas up --model <repo>` prints `Auto-configured <repo> as the qwen3 family: …`, the model becomes ready, and `run.py --require G1,G2,G3,G4,G9` exits 0 (all required groups green) against the auto-configured endpoint — with **no catalog row** for the repo.
- The script's auto-config assertion is load-bearing: it fails if the `Auto-configured …` line is absent (i.e. the model fell through to the bare passthrough) or if a `warning: serving … as plain chat` line appears (i.e. it was treated as unknown-family). This is what distinguishes "auto-configured & agent-grade" from "merely served."
- **Negative control** (run once at authoring, not in CI): temporarily point the gate at a spec that does **not** classify (e.g. force the bare path) and confirm the script's auto-config assertion **fails** — proving the assertion exercises the `Classify` branch and would catch a regression that silently dropped auto-config to bare. Restore.
- Prior groups stay green: the existing `Conformance (llama.cpp)`, `Conformance (two-process)`, and `Conformance (M3)` jobs are unchanged and still pass (cumulative exit-criteria rule).

## Permissions

None new. The gate reaches public Hugging Face metadata + weights for the chosen repo (the existing P8.1 token path covers gated repos, not needed for a public Qwen repo) and the local serving path. No new secrets, no new external service.

## Risks

- **Per-PR dependency on Hugging Face availability.** G23 downloads the gate model's GGUF from HF at engine boot, so a HF outage could red the job. Mitigated by caching the engine's `-hf` download dir keyed on the repo id (cold-cache first run only) — the same exposure the existing catalog store cache already has (catalog gguf models also download from huggingface.co on a cache miss). If HF flakiness proves chronic, the fallback is to mirror the gate model into the content-addressed store as a pinned fixture, but that weakens the "real bring-your-own repo" fidelity, so it is a last resort, not the default.
- **Gate-model drift / unavailability.** A specific HF repo could be renamed, re-quantized, or pulled. Mitigated by selecting a Qwen-published official repo (stable), pinning the revision in the script if needed, and documenting the selection criteria (small, known-family, GGUF, not a catalog name) so the repo is swappable without re-planning.
- **Thin auto-config signal on the CPU/llama.cpp tier.** Because llama.cpp drives tool-calling from the chat template, the qwen3 family's `engineArgs` are largely empty there, so the _parser-flag_ dimension of auto-config is not exercised per-PR — only classification + reasoning gating + sampling + context. Mitigated by (a) asserting the `Auto-configured …` line so classification is proven, (b) requiring G4 so reasoning gating is exercised, and (c) recording the parser-flag families (vLLM/SGLang `--tool-call-parser …`) as the nightly GPU-breadth follow-on in `m8-acceptance.md` — the same per-PR-CPU / nightly-GPU tiering M2/M3 used.
- **CPU-tier model capability.** A 0.6B model must still pass the structural G3/G9 tasks at temperature 0. Mitigated by the suite's structural-not-content design (tasks any competent model passes) and the existing precedent that the catalog `qwen3-0.6b` clears G1–G10 on the CPU tier today; if the no-catalog 0.6B repo underperforms, bump to a ~1.5B known-family GGUF repo (still CPU-feasible).

## Deferred (to follow-ups / nightly)

Tracked in `m8-acceptance.md` and [open-questions.md](open-questions.md); it does not gate M8-done.
- **Auto-config of a local safetensors directory** — stays bare passthrough / `--require-verified`-refusable (carried from P8.2–P8.4); not part of the G23 gate.
- **Real Claude Code drop-in on an auto-configured model** — the capable/GPU acceptance tier (as for M0), not the per-PR CPU gate; G9's agent-SDK loop is the per-PR agent proof.
