# M8 Phase 4 (P8.4) — middle-case behavior + PR funnel

> Build-ready breakdown of **M8 Phase 4** from [m8-build-plan.md](m8-build-plan.md) ("middle case + funnel"), under the ratified [ADR-0015](decisions/0015-bring-any-model-auto-configuration.md). Phases 1–3 built the read-only metadata→`Capabilities` layer ([P8.1](m8-p8.1-build-plan.md)), the family map + metadata-driven serving ([P8.2](m8-p8.2-build-plan.md)), and the load/fit gate that fails fast on an unloadable architecture or an oversized model ([P8.3](m8-p8.3-build-plan.md)). That leaves the **middle case** of ADR-0015's three-way verdict unhandled: a model the pinned engine **can** load and that **fits**, but whose **family Atlas has no agent-config for** (`Classify` returns false). Today such a model serves **silently** on the bare passthrough — no parser flags, no reasoning gating, and no signal to the user that tool-calling/reasoning may misbehave. Phase 4 turns that silence into ADR-0015 Decision 3b's honest behavior: **serve plain chat, but warn clearly and point at the exact one-line PR that would add agent-config for the family** — plus a `--require-verified` opt-out for users who would rather refuse an unverified model than serve it best-effort.

## Goal

`atlas up --model <repo>` / `atlas run` on a **loadable, fitting, but unknown-family** Hugging Face model now **serves chat as before, with a clear startup warning** that names the model's architecture/type, states that Atlas has no tested tool-call/reasoning config for it (so agent behavior is best-effort), and gives the exact contribution pointer — the family map file (`internal/modelmeta/family.go`) and the one-line PR to add the family — mirroring the arch-gate's existing "open a PR" funnel ([arch.go](../../internal/modelmeta/arch.go) `archReason`). A new `--require-verified` flag turns that middle case into a **clean refusal** instead (for users who want only models with tested agent-config). `atlas inspect` previews the same funnel: a loadable+fitting unknown-family model shows the "add a family here" pointer alongside its verdict. A **contributor doc** explains the one-file add and ties it to a conformance case.

This realizes ADR-0015 Decision 3's three-way verdict in full: **(a)** known family + loadable + fits → configure & serve (P8.2); **(b)** loadable + fits but unknown family → **warn-and-serve chat, refusable with `--require-verified`** (this phase); **(c)** un-loadable arch _or_ won't fit → the clean pre-download failure (P8.3). After P8.4 the only raw-spec paths that stay **silent** are the ones inspection can't reach at all (offline, gated, a local safetensors dir) — unchanged best-effort, and refusable under `--require-verified`.

## What already exists (seams this phase extends)

- **`resolveRaw`** — [internal/cli/resolve.go](../../internal/cli/resolve.go:114): after a successful inspection it runs the P8.3 `gateLoadFit` (loadable/fits hard-fail), then `modelmeta.Classify`. A **known** family applies parser `engineArgs`/reasoning/sampling/context and prints `Auto-configured …`. An **unknown** family currently falls through to the bare plan **with no message** — this is the exact branch (resolve.go:145) Phase 4 extends with the warn / `--require-verified` refuse.
- **The `force` plumbing** — `force bool` threads up/run opts → `startModels` → `newEngineRuntime` → `engineRuntime.force` → `start` → `resolveModel` → `resolveRaw` ([models.go](../../internal/cli/models.go:73), [up.go](../../internal/cli/up.go:61), [run.go](../../internal/cli/run.go)). `--require-verified` is a sibling boolean that threads the **same** path (single-node `up`/`run` only; the fleet worker leaves it false, as it does `force`/`quant`).
- **`modelmeta.Classify`** — [family.go](../../internal/modelmeta/family.go:93): returns `(Family, ok)`; `ok=false` is the unknown-family signal. `familyToken(c)` exposes the normalized token (or `""` when there is no arch/type string at all). `FamilyUnknown = "unknown"` is the verdict value.
- **`archReason`** — [arch.go](../../internal/modelmeta/arch.go:81): the model for the funnel message — it names the engine + pinned version, the rejected arch, the upstream page, and "add the architecture to internal/modelmeta/arch.go and open a PR". Phase 4's unknown-family message is the **family-map analogue**, pointing at `internal/modelmeta/family.go` instead, and lives beside it in `modelmeta`.
- **`atlas inspect` presentation** — [inspect.go](../../internal/cli/inspect.go:134) `presentInspect`: already prints `family: unknown` and `parsers: (none — family unknown; served chat-only)` for the middle case. Phase 4 appends the contribution pointer when the model is **loadable + fits** but the family is unknown (the actionable preview of the warn-and-serve path).
- **User-facing models guide** — [website/.../guides/models.md](../../website/src/content/docs/guides/models.md): the "Serving your own weights" section still says raw weights are "best-effort". The **full** reconciliation of this page + the launch post is assigned to **Phase 5** ("Reconcile public docs"); P8.4 adds the **contributor** doc only and leaves the public-prose rewrite to P8.5 to avoid double-touching it.

## Decisions taken

### Product (owner) — already settled in ADR-0015

- The middle case (3b) **defaults to warn-and-serve chat**, with a **`--require-verified` opt-out** to refuse it instead (resolved Q3). The warning is "clearly labelled at startup; refusable." The contribution funnel (name the file + the one-line PR) is ADR-0015 Decision 2's "extending support is a normal PR." No new product decision is open in this phase.

### Technical (lead dev)

- **The funnel message lives in `modelmeta`, beside `archReason`.** A new `modelmeta.UnknownFamilyReason(c Capabilities) string` renders the pointer: it names the model's `architecture`/`model_type` (so the contributor knows what token to add), states that Atlas has no tested tool-call/reasoning config for that family, and points at `internal/modelmeta/family.go` + "open a PR" — symmetric with `archReason` so the two funnels read alike and model-knowledge stays in the leaf package (no `worker` import). The `cli` layer only decides _when_ to print it.
- **`requireVerified` mirrors `force` exactly.** A `requireVerified bool` threads the same parameter path as `force` (a sibling field on `engineRuntime`, a sibling flag on `up`/`run`, false on the fleet path). It is **not** a `modelmeta` concept — `modelmeta` reports facts (loadable/fits/family); the _policy_ of refusing an unverified model is a `cli` serving-path decision, exactly like the warn.
- **`--require-verified` refuses whenever a known family cannot be confirmed**, not only the inspected-unknown case. "Require verified" means "serve only models Atlas has tested agent-config for." That is true for a catalog model and for a raw spec that classifies to a known family; it is **false** for a loadable-unknown-family spec **and** for a spec inspection could not read at all (offline/gated/local safetensors dir — we cannot confirm a family, so we cannot call it verified). So under `--require-verified`: a catalog model and a known-family raw spec serve unchanged; an unknown-family raw spec and an un-inspectable raw spec both **refuse** with an actionable message. Without the flag, behavior is unchanged except for the new warning on the inspected-unknown branch (an un-inspectable spec stays **silent** bare passthrough, as today — Phase 4 adds no noise to the path it can say nothing about).
- **Ordering inside `resolveRaw` is unchanged; the new branch sits after the family check.** `gateLoadFit` (loadable then fits, P8.3) still runs first — an unloadable/oversized model is the (c) hard failure regardless of `--require-verified`. Only a model that passes the gate reaches the family decision, where Phase 4 adds: known → auto-config (unchanged); unknown → warn (or refuse under `--require-verified`). The un-inspectable early return (resolve.go:120) gains the `--require-verified` refusal but is otherwise unchanged.
- **`--force` and `--require-verified` are orthogonal and may combine.** `--force` skips the **arch-loadability** refusal (P8.3, the (c) gate); `--require-verified` tightens the **family** middle case (3b). A user could `--force --require-verified` (force an unlisted arch but still demand a known family) — both apply independently at their own decision points; no special-casing needed.
- **`inspect` gains a trailing pointer line, not a verdict-field change.** The `Verdict` struct is unchanged (family/loadable/fits already carry the facts). `presentInspect` appends one human line — the `UnknownFamilyReason` pointer — only when `family == FamilyUnknown && loadable == "yes" && fits != "no"`, so the funnel shows exactly where it is actionable. `--json` is unchanged (the facts are already present; the pointer is a presentation affordance, not new data).

## Data model

No DB/migration, no new on-disk artifact, no `Capabilities`/`Verdict` schema change. The funnel message is computed from the existing `Capabilities`; `requireVerified` is a transient CLI flag. The `inspect-cache` JSON is untouched.

## Sub-phases

### P8.4a — warn-and-serve middle case + `--require-verified` (serving path + inspect surface)

**Scope.** Turn the silent unknown-family fall-through into the honest middle case, add the opt-out flag, and preview the funnel in `inspect`:

- New `modelmeta.UnknownFamilyReason(c Capabilities) string` in [family.go](../../internal/modelmeta/family.go) (beside `Classify`), mirroring `archReason`: names the arch/model_type, states no tested agent-config exists for the family, points at `internal/modelmeta/family.go` + "open a PR".
- `resolveRaw` ([resolve.go](../../internal/cli/resolve.go)): thread a `requireVerified bool` (sibling to `force`). On the **inspected, gated-passed, unknown-family** branch — if `requireVerified` → return an error (the `UnknownFamilyReason` message, framed as a refusal); else → print the warning to the command's output and serve the bare plan (unchanged serving). On the **inspection-failed** early return — if `requireVerified` → return an error stating the family could not be confirmed; else unchanged (silent bare passthrough). A known family is unaffected by either path.
- Thread `requireVerified` through `resolveModel` → `engineRuntime` (new field) → `start` → `startModels` → `newEngineRuntime`, and add the `--require-verified` flag to `up` and `run` (mirroring `--force` wiring; false on the fleet worker path).
- `inspect` ([inspect.go](../../internal/cli/inspect.go)): in `presentInspect`, append the `UnknownFamilyReason` pointer when `family == FamilyUnknown && loadable == "yes" && fits != "no"`.

**API.** No HTTP/openapi change — CLI + library only. New `--require-verified` flag on `atlas up` and `atlas run`. New `inspect` pointer line (human output only; `--json` unchanged).

**Acceptance (automated, hermetic — normal `go test` gate).**

- `UnknownFamilyReason` unit test: a `Capabilities` with an unknown arch/type → a non-empty message naming the arch/type **and** `internal/modelmeta/family.go`; symmetry sanity (it does not name `arch.go`).
- `resolveRaw` middle case (httptest `ATLAS_HF_ENDPOINT` + injected capacity): a **loadable, fitting, unknown-family** spec → returns the **bare** plan (no parser `engineArgs`, `reasoning=false`) **and** emits the warning (capture command output); the same spec with `requireVerified=true` → returns an **error** naming the family/arch + `family.go`, and (assert) reaches no weight-download path.
- Regression guards: a **known-family** spec → auto-config plan + the `Auto-configured …` note and **no** warning, with and without `requireVerified` (a known family is verified, so `--require-verified` serves it unchanged); a spec whose metadata fetch **404s** → bare passthrough, **no** warning, no error when `requireVerified=false`, and an **error** when `requireVerified=true` (family unconfirmable).
- Orthogonality: `--force` past an unlisted arch on an unknown-family model still warns (or refuses under `--require-verified`) on the family axis — the two flags act independently.
- `inspect` command test (extending P8.1–P8.3): a loadable + fitting unknown-family fixture → output includes the `family.go` pointer line; a **known-family** fixture → **no** pointer line; an **unloadable** fixture → no family pointer (the loadable=no reason already carries the arch funnel).
- Negative control: remove the warn/refuse branch in `resolveRaw` → the middle-case test no longer sees the warning (and the `--require-verified` test no longer errors), confirming the test exercises the new branch.

### P8.4b — contributor doc: add a model family (the PR funnel)

**Scope.** Document the one-file add the warn/refuse messages point at, so the funnel lands somewhere actionable:

- New contributor doc `docs/internal/contributing-model-families.md`: what a `families` entry in [family.go](../../internal/modelmeta/family.go) is (the `Name` token, `Reasoning`, per-engine `toolCall`/`reasoning` parser names), how `normalizeFamily` maps a model's `model_type`/architecture to the token, when a new **architecture** also needs adding to [arch.go](../../internal/modelmeta/arch.go), and the rule that **a new family entry ships with a conformance case** (M8 Phase 5) — "earned by the suite, not vibes" (ADR-0015 Decision 2). Cross-link ADR-0015 and the M8 build plan.
- Link the new doc from the docs map in [README.md](../../README.md) (the repo convention) and from [m8-build-plan.md](m8-build-plan.md) Phase 4.

**API.** None — docs only.

**Acceptance.** Docs-only slice — the gate is `make fmt` + markdownlint clean and the `check.sh` link/format pass (no broken relative links). No new automated test; the doc's correctness is that its file/field references match the code it points at (verified by reading `family.go`/`arch.go` at authoring time). The public-prose reconciliation of `website/.../guides/models.md` + the launch post stays **Phase 5**.

## Permissions

None new. Resolution reaches only public/user-tokened Hugging Face metadata (the existing P8.1 token + P8.3 `?blobs=true` listing) and local files; serving is the existing worker path. `--require-verified` only **narrows** what is served.

## Risks

- **Warning fatigue / noise on the common bring-your-own path.** A loadable-unknown-family model is exactly the "bring your own and it mostly works for chat" case, so the warning fires often. Mitigated by keeping it to a single, actionable line (not a wall), printing it once per model at startup (not per request), and pairing it with the concrete fix (the one-line PR) rather than a vague caveat. The verbatim-serve behavior is unchanged — the warning never blocks.
- **`--require-verified` over-refusing.** Because it refuses every spec without a confirmed known family — including un-inspectable ones (offline/gated/local safetensors) — a user who sets it expecting only "unknown family" to be blocked might be surprised when an offline repo is refused. Mitigated by a precise message (distinguish "unknown family: <arch>" from "could not confirm a family: inspection failed (offline/gated/local dir)") so the cause is clear, and by it being strictly opt-in (default is unchanged warn-and-serve).
- **Funnel message drift from the code it points at.** If `family.go`'s file path or the contribution flow changes, the message and the P8.4b doc go stale. Mitigated by computing the message in `modelmeta` next to `family.go` (so a move is local) and by the doc being a single page the Phase-5 conformance work revisits.
- **Inspect pointer shown when not actionable.** Guarded by the `loadable=="yes" && fits!="no"` condition so the family funnel never competes with the arch funnel (an unloadable model shows only the arch reason) or suggests adding a family for a model that won't fit anyway.

## Deferred (to later M8 phases / follow-ups)

- The **conformance G-group** that auto-configures a catalog-less **known-family** model and runs the agent tool-use/streaming gates, and the **public-docs + launch-post** reconciliation (`website/.../guides/models.md` "best-effort" → auto-config + honest middle case, and the launch post's "bring your own" paragraph) — **Phase 5**.
- Inspecting/auto-configuring (and thus classifying) a **local safetensors directory** — stays bare passthrough; under `--require-verified` it refuses as "family unconfirmable" (carried over from P8.2/P8.3's deferral of local-dir inspection).
- A `--require-verified`-style **global default** (e.g. a config/env to make refuse-unverified the default) — the flag is per-invocation for now.
