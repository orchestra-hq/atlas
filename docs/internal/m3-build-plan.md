# M3 build plan

The ordered path from M2's operable fleet to a fleet that is **differentiated and trustworthy for real agent stacks**: keep multi-turn conversations on warm hardware, serve the embedding/rerank model classes a RAG stack needs, record an audit trail of who changed what, and spill overflow to a real provider instead of dropping it. This refines the M3 milestone in [roadmap.md](../roadmap.md); design truth still lives in [architecture.md](architecture.md) and the relevant ADRs.

M3 is the roadmap's "ecosystem & differentiation deepeners (pick by traction)" milestone, so its first job is to **pick**. Of the five candidate threads, M3 takes the four that compound M2's momentum and serve Atlas's thesis — _point your own agents at your own hardware_ — and explicitly defers the two heaviest:

- **In:** prefix/session-affinity routing, embeddings + reranker model classes, an audit log, cloud-fallback passthrough.
- **Deferred:** a full HA control plane (Postgres, durable admission queue, multi-replica) — heavy ops infra with thin demand at current fleet sizes; ADR-0008/ADR-0010 already left the doors open (swap the `database/sql` driver; the in-memory queue is isolated), so it is pulled forward only when traction demands, as its own future milestone. The **hosted control-plane offering** is a business/open-core decision, not a build task, and stays out.

The audit log is deliberately **split out** of the roadmap's "HA control plane; audit log" bundle: it is light, independent, and high-value for the operate-a-real-fleet trust story, so it ships here while full HA waits.

## Build-time technical decisions

Choices recorded here so they don't get re-litigated mid-build:

1. **Affinity is a hint layered on ADR-0010 selection, never a hard pin.** Prefix/session-affinity routing extends — does not replace — the least-in-flight selection and backpressure of [ADR-0010](decisions/0010-load-balancing-and-backpressure.md). The gateway prefers the replica a conversation is affine to **only while that replica is within a load tolerance of the least-loaded one**; past the tolerance, load wins and the request moves. Affinity must never reintroduce a hang or a 5xx that backpressure exists to prevent. See [ADR-0011](decisions/0011-prefix-session-affinity-routing.md).
2. **Embeddings and rerank are new _model classes_, not a new transport.** A catalog/model `class` (`chat` | `embedding` | `reranker`) routes a request to the right endpoint and the right engine capability. Embeddings are served on the OpenAI-compatible `POST /v1/embeddings` (the Anthropic Messages API has no embeddings surface, so there is nothing to mirror); rerank is served on a native Atlas endpoint following the de-facto Cohere `/v1/rerank` shape. Engines are wrapped, not reimplemented ([ADR-0001](decisions/0001-orchestrate-engines-not-build-one.md)): vLLM/SGLang/llama.cpp already expose embedding (and scoring/rerank) tasks. See [ADR-0012](decisions/0012-embeddings-and-reranker-model-classes.md).
3. **The audit log reuses the ADR-0008 SQLite store; no new ADR.** It is an append-only table in `internal/db` recording actor + action + target + result + timestamp for control-plane mutations: model deploy/scale/stop and worker drain/remove (HTTP admin handlers, actor = the admin key id) and API key create/revoke (the local `atlas keys` CLI, actor = `cli`/`system`). Runtime upgrade is deliberately **out of scope**: `atlas runtime upgrade` is a worker-local CLI operation that never reaches the control plane (and a worker may be a separate machine with no access to the control-plane store), so it cannot be — and is not — recorded here. Surfaced via an admin read API and `atlas audit`. Like M2's observability work, the schema and the captured action set are a convention recorded in this doc, not a load-bearing architectural decision. Tamper-evidence (hash-chaining) is noted as a future option, not built.
4. **Cloud-fallback is opt-in, clearly labeled, and separately billed.** Spilling overflow to a real upstream provider (Anthropic or OpenAI, operator-supplied key) is **off by default** and enabled per deployment/model/key. A cloud-served response is labeled out-of-band (`x-atlas-served-by: cloud` header + separate usage attribution) — never by mutating the response body, which would break the drop-in promise (CLAUDE.md rule 3). Cloud-served tokens are recorded as a distinct ledger class because they cost real money. See [ADR-0013](decisions/0013-cloud-fallback-passthrough.md).
5. **Full HA and the hosted offering are out of M3.** Durable/HA admission and a multi-replica control plane are a later milestone; the hosted offering is a separate business decision. M3 must not grow a Postgres dependency or a commercial surface.

The three new ADRs ([0011](decisions/0011-prefix-session-affinity-routing.md), [0012](decisions/0012-embeddings-and-reranker-model-classes.md), [0013](decisions/0013-cloud-fallback-passthrough.md)) are **proposed** alongside this plan and flip to `accepted` as each phase starts, so the design details harden under review before code lands.

## Phase notes

**Phase 1 — prefix/session-affinity routing.** [ADR-0010](decisions/0010-load-balancing-and-backpressure.md) deferred this to M3 with intent: least-in-flight can bounce a conversation between replicas, forgoing the warm prefix cache that M2's SGLang adapter (and any prefix-caching engine) maintains. Multi-turn agent loops — Claude Code, the Agent SDK — are exactly the workload that pays for that miss on every turn, since each turn re-sends the whole growing conversation. The gateway derives a **routing key** per request (a hash of the stable conversation prefix — system prompt + leading messages — with an explicit session header honored when present) and consistent-hashes it to a replica. That affine replica is chosen **only while it stays within a configurable load tolerance of the least-loaded replica**; beyond the tolerance, the request falls back to plain least-in-flight, so affinity never defeats the backpressure it sits on top of. It is entirely gateway-side, no new wire protocol — the affinity layer lives in the same admission/dispatch layer ADR-0010 introduced, reading the same in-flight counters. New `/metrics` series: affinity hit/miss and a per-replica warm-key gauge, surfaced in `atlas top`.

Phase 2 is the largest thread — it widens Atlas from a chat-inference platform to the inference platform a self-hosted RAG/agent stack needs, where embeddings and rerank are first-class, not bolt-ons — so it lands in two sub-phases that each demo independently: **2a** builds the model-`class` abstraction and the OpenAI-standard embeddings half; **2b** adds the native rerank surface on top of that machinery.

**Phase 2a — model-`class` abstraction + embeddings.** The foundational half, where the bulk of the work lives. A catalog/model **`class`** field (`chat` | `embedding` | `reranker`, defaulting to `chat`) threads from the catalog through the scheduler (placement is the same VRAM-fit logic; these models simply do not stream and have no tool loop) to the gateway, which routes by class to the right endpoint and rejects a mismatched request (e.g. an embeddings call against a chat model) with a clean Anthropic/OpenAI-shaped error. The first non-chat class is taken end to end via **`POST /v1/embeddings`** (OpenAI shape — there is no Anthropic embeddings surface), wrapping engine capabilities that already exist (vLLM/SGLang embedding tasks, llama.cpp `/embedding`) per [ADR-0001](decisions/0001-orchestrate-engines-not-build-one.md) — Atlas does not compute embeddings, it routes to an engine that does. The shared `internal/engines/openaichat` client grows a sibling embeddings call (or a parallel small client) so vLLM, SGLang, and MLX reuse one translation as they do for chat. The starter catalog gains at least one embedding model with a pinned digest (the M0 pinning rule still holds). Exit is the embeddings half of G20.

**Phase 2b — reranker.** The thin second half, riding the 2a class machinery. It adds the `reranker` class value and a native **`POST /v1/rerank`** (Cohere-shaped, the de-facto convention — there is no OpenAI rerank standard to mirror), wrapping the engines' scoring/rerank capability through the same shared client: one more class value, one endpoint, one wrapped capability. The starter catalog gains a pinned reranker. Splitting it out lets the embeddings drop-in (the SDK-backed, higher-demand half) land and demo before the native rerank surface; 2b completing brings G20 fully green.

**Phase 3 — audit log.** The lightweight trust item split out of the HA bundle. An append-only `audit` table in the [ADR-0008](decisions/0008-control-plane-persistence-and-api-keys.md) SQLite store records every control-plane mutation — model deploy/scale/stop, worker drain/remove, and API key create/revoke — with the actor, the action, the target, a timestamp, and the result. The HTTP mutations are written at the admin handlers' choke point: a `RequireAdminAudited` middleware that wraps the existing `RequireAdmin` gate, so it reuses the same store, auth, and middleware as the admin surface (no new auth, no new persistence dependency) and records the admin key id as actor. Key management runs through the local `atlas keys` CLI rather than an HTTP handler, so those mutations record themselves directly against the store with actor `cli` (or `system` for the bootstrap default key). Runtime upgrade is worker-local and never reaches the control plane, so it is out of scope (decision 3). An admin read API (`GET /admin/audit`) plus `atlas audit` (list, filter by actor/action/target/time) surface it; records are immutable (insert-only, no update/delete path) and durable across restart. Hash-chaining for tamper-evidence is recorded as a future option in the ADR-0008 lineage, not built here.

**Phase 4 — cloud-fallback passthrough.** The differentiator, placed last because it touches the drop-in trust promise and introduces an outbound dependency, so it earns the most design scrutiny ([ADR-0013](decisions/0013-cloud-fallback-passthrough.md)). When a request would otherwise shed under ADR-0010 backpressure (or hit an undeployed but mappable model) and cloud-fallback is **enabled** for that deployment/model/key, the gateway forwards it to a configured upstream provider using an operator-supplied key, translating Atlas's already-canonical Anthropic/OpenAI request straight through. The response is **labeled out-of-band** — an `x-atlas-served-by: cloud` header and a distinct usage attribution — never by editing the body, so SDK parsing is untouched (CLAUDE.md rule 3). Cloud-served tokens are billed as a separate ledger class (they are real spend, not local capacity). Fallback is **off by default**; enabling it is an explicit operator choice with explicit upstream credentials. The same mechanism cleanly degrades to ADR-0010's 429/529 when it is disabled, so the backpressure contract is unchanged for anyone who does not opt in.

## Conformance groups added in M3

These extend the suite defined in [conformance-suite.md](conformance-suite.md).

### G19 — Prefix/session-affinity routing

A conversation sent repeatedly across turns lands on the same replica while that replica has capacity, so a prefix-caching engine reuses its warm cache (affinity hit). Under load that pushes the affine replica past the configured tolerance, the request falls back to least-in-flight rather than queueing behind a busy replica — never a hang or a 5xx, and the backpressure semantics of G16 still hold. Affinity hit/miss and per-replica warm-key counts appear in `/metrics` and `atlas top`.

### G20 — Embeddings + reranker model classes

A deployed embedding model serves `POST /v1/embeddings` with correct-dimension vectors for the OpenAI SDK drop-in; a deployed reranker serves `POST /v1/rerank` and orders documents by relevance. A request sent to the wrong class (embeddings against a chat model, or vice versa) returns a clean, well-formed error, not a 5xx. Class-aware scheduling places embedding/reranker models on capable workers by the same VRAM-fit policy as chat models. The group lands across the two sub-phases: phase 2a brings the embeddings half (and the class abstraction the rejection check rides) green, phase 2b completes it with the rerank half.

### G21 — Audit log

Every control-plane mutation — model deploy/scale/stop, worker drain/remove, and API key create/revoke — produces an audit record carrying the actor (the admin key id for an HTTP action, `cli`/`system` for local key management), the action, the target, a timestamp, and the result. Records are append-only (no API mutates or deletes them) and durable across a control-plane restart. `atlas audit` (and the `GET /admin/audit` read API) lists them and filters by actor, action, target, and time window. Runtime upgrade is a worker-local operation outside the control plane and is not captured (build-plan decision 3).

### G22 — Cloud-fallback passthrough

With fallback enabled for a model: load beyond local capacity that G16 would shed is instead served by the configured upstream provider, and the response is labeled `x-atlas-served-by: cloud` with its tokens attributed to the cloud ledger class — the response body itself is byte-for-byte a normal Atlas response, so the SDK is unaffected. With fallback disabled (the default): the identical overflow sheds with the ADR-0010 429/529 envelope, unchanged. Usage reporting separates cloud-served from locally-served tokens.

## Testing tiers

M3 reuses the established tier structure. Most of M3 is provable on the CPU per-PR tier — the routing, class, audit, and fallback logic are gateway/store concerns testable against fakes and llama.cpp — with the engine-breadth and warm-cache assertions joining the nightly capable tier.

| Tier        | What                                                                                                                                                       | When              |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------- |
| Unit        | Routing-key derivation + affinity-vs-load tolerance; class routing/rejection; audit record shape + append-only invariant; fallback enable/label/bill logic | Every PR          |
| Integration | Affinity and fallback against a fake worker + fake upstream stub; `/v1/embeddings`/`/v1/rerank` and `atlas audit` against a running gateway                | Every PR          |
| Conformance | Real llama.cpp, two-process local deployment: G19 affinity routing, G20 embeddings (llama.cpp `/embedding`), G21 audit, G22 fallback (stub upstream)       | Every PR          |
| Full matrix | Affinity warm-cache reuse on SGLang (prefix cache) + rerank on a GPU engine for G19/G20 on the capable/nightly tier; embedding/reranker catalog rows       | Nightly + release |

The per-PR conformance tier proves affinity selection, class routing, the audit trail, and labeled fallback on llama.cpp (CPU, no special hardware). The genuine prefix-cache _reuse_ that affinity exists to win, and rerank/embedding breadth across the GPU engines, join the nightly capable tier alongside the existing G17/G18 runs — the same dormant MLX/CUDA runners tracked in [open-questions.md](open-questions.md).
