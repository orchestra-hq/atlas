# M8 Phase 2 (P8.2) — family map + auto-derived serving

> Build-ready breakdown of **M8 Phase 2** from [m8-build-plan.md](m8-build-plan.md) ("family map + serve"), under the ratified [ADR-0015](decisions/0015-bring-any-model-auto-configuration.md). Phase 1 ([P8.1](m8-p8.1-build-plan.md)) built the read-only metadata→`Capabilities` layer and `atlas inspect`, with `family` reported as `pending (Phase 2)`. Phase 2 supplies that family knowledge and **wires it into resolution**, so a known-family model that is _not_ in the catalog serves agent-grade (tool-call + reasoning parsers applied) from one `atlas up --model <repo>`.

## Goal

A user runs `atlas up --model <a-known-family-HF-or-GGUF-model-not-in-the-catalog>` and gets the **same agent-grade serving config a catalog entry would give** — the right tool-call/reasoning parser flags for the target engine, reasoning gating, the author's sampling defaults, and a context-window hint — derived automatically from the model's own metadata plus an in-code **family → agent-config map**. The map is the extension point ADR-0015 Decision 2 describes: adding a family is a normal PR (later gated by the Phase-5 conformance case). An **unknown** family is unchanged from today (bare passthrough); the warn-and-serve / `--require-verified` middle-case stays Phase 4.

## What already exists (seams this phase extends)

- **`internal/modelmeta`** — [modelmeta.go](../../internal/modelmeta/modelmeta.go) defines the normalized `Capabilities` record (both HF and GGUF paths produce it) and the staged `Verdict`, whose `Family`/`Loadable`/`Fits` fields read `Pending` until later phases fill them. `verdictFor` builds the Phase-1 verdict. Phase 2 adds the family classifier here and flips `Verdict.Family` from `Pending` to a real answer.
- **`atlas inspect`** — [internal/cli/inspect.go](../../internal/cli/inspect.go) presents `Result`; `pendingLine` annotates the family row with "M8 Phase 2". Phase 2 makes that row show the detected family (and the parser flags it implies).
- **The metadata cache** — `readInspectCache`/`writeInspectCache` in [inspect.go](../../internal/cli/inspect.go:189), keyed by `repo@revision` under the state dir, with a 24h TTL on mutable refs. Phase 2b reuses these so `up` does not re-fetch what `inspect` already cached.
- **Resolution** — [internal/cli/resolve.go](../../internal/cli/resolve.go): `resolveModel` returns a `resolvedModel{served, modelArgs, engineArgs, ctxHint, sampling, reasoning, class}`. The catalog branch fills all fields; the **raw-spec branch returns only `served`+`modelArgs` (bare passthrough)** — exactly the gap Phase 2b closes. Callers: [run.go:86](../../internal/cli/run.go:86) and [models.go:98](../../internal/cli/models.go:98) (`engineRuntime.start`), both of which hold a `stateDir`.
- **The catalog as the family-knowledge source** — [catalog/starter.yaml](../../catalog/starter.yaml) already encodes per-engine parser flags in `engine_args`: vLLM `--enable-auto-tool-choice --tool-call-parser hermes --reasoning-parser qwen3` (qwen3-8b), SGLang `--tool-call-parser qwen25 --reasoning-parser qwen3` (qwen3-8b-sglang) / `--tool-call-parser qwen25` (qwen2.5-7b-sglang), vLLM `--tool-call-parser glm47 --reasoning-parser glm45` (glm-5.1). Phase 2 **lifts** this into the family map; it does **not** change the catalog (ADR-0015 Decision 7: the catalog keeps blessed examples and remains the override/pin path).
- **Worker config** — [internal/worker/worker.go](../../internal/worker/worker.go:28) engine constants and `worker.Config` (`ExtraArgs`, `Reasoning`, `Temperature`/`TopP`, `ContextWindow`) consume exactly the fields `resolvedModel` carries.

## Decisions taken

### Product (owner) — already settled in ADR-0015

- Resolution becomes metadata-driven for raw specs (Decision 1); the supported-models surface is an **in-code family map**, not a catalog/community artifact (Decision 2); the catalog path and local-path path are unchanged and the catalog remains the override/pin surface (Decision 7); unknown-family **warn-and-serve / `--require-verified`** is **Phase 4**, so Phase 2's unknown-family behavior is the current bare passthrough (Decision 4); GGUF multi-quant uses a documented default + `--quant` override (resolved Q2).

### Technical (lead dev)

- **The family map lives in `internal/modelmeta` (`family.go`).** It is the package that already owns `Capabilities` and is imported by both `inspect` and (Phase 2b) `resolveModel`, and it is a network/parse-free leaf otherwise — keeping the map there means one home for "model knowledge." It uses **bare engine name strings** (`"vllm"`, `"sglang"`, `"llamacpp"`, `"mlx"`, matching `worker.Engine` values) so `modelmeta` stays free of a `worker` import, as it is today.
- **Classification keys on a normalized family token**, derived from `model_type` (HF `config.json`) or `general.architecture` (GGUF header), with `architectures[0]` as a fallback signal. Tokens: `qwen2`, `qwen3`, `glm`, `gemma`, `llama`. Normalization is conservative (exact/prefix match into the seed table); **no match → not a known family**, which keeps an unrecognized model on the safe bare path rather than mis-applying a parser.
- **The map is engine-aware.** The same family needs different flags per engine (e.g. qwen3 tool-call parser is `hermes` on vLLM but `qwen25` on SGLang; llama.cpp and MLX are template-driven and take **no** parser flags). A `Family` therefore carries per-engine parser config, and `(Family).EngineArgs(engine)` renders the flag list for the target engine (empty for template-driven engines or an engine the family has no entry for).
- **Reasoning is family-level** (engine-agnostic: it gates the thinking kwarg in `worker.Config.Reasoning`). Sampling is **not** family-level — it comes from the model's own `generation_config.json` (`Capabilities.Sampling`), per the ADR's "sampling is partly auto-derivable" row; the family map carries no sampling.
- **Seed only what is evidenced + low-risk.** qwen2, qwen3, glm get full vLLM/SGLang parser config (lifted from `starter.yaml`). gemma and llama are seeded for the **template-driven** path only (reasoning gating, no parser flags) — low risk because no parser-name guess is involved; their vLLM/SGLang parser cells are left unset (those combos behave as today) until a conformance case earns them. Additional families/engine cells are ordinary conformance-gated PRs (ADR-0015 Decision 2) — explicitly the extension model, not a Phase-2 backlog.
- **Resolution classifies from cached `Capabilities`, not cached `Verdict`.** `Capabilities` is stable across binary versions; `Verdict` semantics evolve per phase (a pre-P8.2 cache holds `Family:"pending"`). Re-classifying from `Capabilities` makes resolution robust to a stale-schema cache entry.
- **Local vs remote inspection in resolution.** A local `.gguf` path reads its header off disk (no network, no cache); a Hugging Face repo/`-hf` spec fetches metadata via the shared `inspect-cache`. A local safetensors directory is **not** inspected in Phase 2 (rare; stays bare) — noted as deferred. Inspection failure in `resolveModel` is **non-fatal**: it falls back to bare passthrough, so a metadata hiccup never blocks a serve that works today.
- **`ATLAS_HF_ENDPOINT` overrides the metadata host** for resolution (a Hugging Face mirror, and the hermetic test seam, since `up`/`run` carry no `--hf-endpoint` flag the way `inspect` does).

## Data model

No DB/migration. No new on-disk artifact: Phase 2b reuses the existing `inspect-cache` files (the cached `Result` already carries `Capabilities`). The family map is compiled-in Go data.

## Sub-phases

### P8.2a — family map + classifier (library + `inspect` surface)

**Scope.** The family knowledge and its presentation, with **no serving/resolution change**:

- New `internal/modelmeta/family.go`: a `Family` type (canonical `Name`, `Reasoning bool`, per-engine parser config), the seeded family table (qwen2, qwen3, glm with vLLM/SGLang parsers; gemma, llama template-only), `Classify(c Capabilities) (Family, bool)` keying on the normalized family token (`ModelType`/GGUF arch, with `Architecture` fallback), and `(Family).EngineArgs(engine string) []string` rendering per-engine flags (vLLM: `--enable-auto-tool-choice` + `--tool-call-parser <p>` + optional `--reasoning-parser <r>`; SGLang: `--tool-call-parser <p>` + optional `--reasoning-parser <r>`; llamacpp/mlx: none).
- `verdictFor` classifies: `Verdict.Family` becomes the family name or `"unknown"` (no longer `Pending`).
- `atlas inspect` shows the detected family and, when known, the parser flags it would apply for the candidate engine (a preview of what P8.2b will serve); `--json` carries the family. The `family` row's "M8 Phase 2" pending annotation is removed.

**API.** No HTTP/openapi change — CLI + library only.

**Acceptance (automated, hermetic).**

- Table test of `Classify`: a Qwen2.5 fixture (`model_type: qwen2` / arch `Qwen2ForCausalLM`) → family `qwen2`, `reasoning=false`; a Qwen3 fixture → `qwen3`, `reasoning=true`; a GLM fixture → `glm`, `reasoning=true`; a GGUF fixture (`general.architecture: qwen3`) → `qwen3`. An unrecognized `model_type` → not found.
- `EngineArgs` per family/engine: qwen3 → vLLM `[--enable-auto-tool-choice --tool-call-parser hermes --reasoning-parser qwen3]`, SGLang `[--tool-call-parser qwen25 --reasoning-parser qwen3]`, llamacpp/mlx `[]`; qwen2 omits the reasoning-parser; gemma/llama → `[]` for vLLM/SGLang (template-only).
- `inspect` command test (httptest, extending P8.1a's): a Qwen3 fixture now prints `family: qwen3` and the would-be parser flags; `--json` round-trips `Verdict.Family == "qwen3"`.
- Negative control: an unknown-`model_type` fixture prints `family: unknown` and the inspect output applies no parser flags.

### P8.2b — metadata-driven resolution (serving)

**Scope.** Close the bare-passthrough gap in `resolveModel`'s raw-spec branch:

- Thread `stateDir` into `resolveModel` (both call sites have it) so it reuses the `inspect-cache` helpers; refactor the cache helpers if needed so library-level resolution and the CLI command share one implementation.
- In the raw-spec branch: inspect the spec (local `.gguf` → on-disk header; HF repo/`-hf` spec → cached metadata fetch), `Classify` from the resulting `Capabilities`, and **if a known family**, build a full `resolvedModel`: `engineArgs = family.EngineArgs(engine)` (merged with any user `--engine-arg`, which still wins/appends as today), `reasoning = family.Reasoning`, `sampling = caps.Sampling`, `ctxHint = caps.ContextWindow`. An **unknown** family or a failed/sktipped inspection falls back to the current bare passthrough unchanged.
- A short stderr note on the auto-config path ("auto-configured `<repo>` as family `<f>`: <engine args>") so the behavior is visible; this is informational, distinct from the Phase-4 unknown-family **warning**.

**API.** No HTTP/openapi change. No new flag (the warn/`--require-verified` opt-out is Phase 4).

**Acceptance (automated, hermetic — normal `go test` gate; Atlas has no separate integration-tag harness).**

- With metadata served from an httptest fixture server (`ATLAS_HF_ENDPOINT`), `resolveModel(engine=vllm, spec="Qwen/Qwen3-8B")` (a repo **not** in the catalog) returns `engineArgs` containing `--tool-call-parser hermes` and `--reasoning-parser qwen3`, `reasoning=true`, `ctxHint` from the fixture's `max_position_embeddings`, and the author sampling; the same spec with `engine=sglang` returns the `qwen25`/`qwen3` parser set and **omits** vLLM's `--enable-auto-tool-choice`.
- A known-family **local `.gguf`** (hand-built header `general.architecture: qwen3`) on llamacpp resolves to `reasoning=true` with no parser flags (template-driven) — proving the raw-hybrid reasoning-gating gap (`starter.yaml` qwen3-8b-gguf comment) is closed for bring-your-own GGUF.
- Negative control: an unknown-family spec (`model_type: mamba`) returns the bare `resolvedModel` (no `engineArgs`, `reasoning=false`, `ctxHint=0`) — identical to pre-P8.2 behavior; and a metadata-fetch failure (404 host) also falls back to bare.
- Note: "serves and tool-calls correctly on a real engine" is proven by the **Phase-5 conformance gate**, not per-PR — matching how P8.1 deferred end-to-end agent proof. P8.2b's per-PR bar is the resolution-plan assertion above.

### P8.2c — serve-time quant selection for multi-quant GGUF repos

**Scope.** Complete the "bring any GGUF" path begun by P8.1b's inspect-time quant reporting (resolved Q2: default `Q4_K_M`, else nearest; `--quant` overrides):

- A `--quant <name>` flag on `atlas up`/`atlas run` (single-node only; the fleet worker takes models by name from the scheduler) that selects which quantization of a multi-quant GGUF **repo** to serve; absent, the documented default heuristic (prefer `Q4_K_M`, else nearest) picks, reusing the listing `inspect` already produces (`Capabilities.Files`/`Selected`, P8.1b).
- Resolution rewrites the llama.cpp model args to `-hf <repo>:<quant>` (the engine's blessed `repo:quant` form, already documented in `worker.Config.ModelArgs`), so `up` serves the same quant `inspect` reported.

**API.** No HTTP/openapi change — new CLI flag only. `--quant` is plumbed through `engineRuntime`/`newEngineRuntime`/`startModels` into `resolveModel`.

**Acceptance (automated, hermetic).**

- A multi-quant GGUF repo fixture (model API listing several `*.gguf`): resolution with no `--quant` yields `-hf <repo>:Q4_K_M` (matching `inspect`'s default); `--quant Q5_K_M` yields `-hf <repo>:Q5_K_M`; `--quant <unknown>` errors listing the available quant tokens.
- Negative control: `--quant` on a target that is **not** a multi-quant repo (a single local `.gguf`) is a clear error, not a silent no-op.

## Permissions

None new — resolution reaches only public/​user-tokened Hugging Face metadata (the P8.1 token handling) and local files; serving is the existing worker path.

## Risks

- **Wrong parser name for a family/engine** → tool-calling misbehaves. Mitigated by seeding only evidenced combinations from `starter.yaml`, leaving unproven combos unset (safe bare/middle behavior), and the Phase-5 conformance gate that must accompany each family.
- **`up` now fetches metadata for raw HF specs** (latency, an offline failure mode that did not exist). Mitigated by the shared cache (a prior `inspect`/`up` is instant) and the non-fatal fallback to bare passthrough on any inspection error — `up` never becomes _less_ able to serve than today.
- **Arch/model_type string drift across model releases.** Mitigated by tolerant normalization (unknown → bare, never a crash) and fixtures pinned from real repos.
- **Cache schema skew** (a pre-P8.2 cached `Verdict.Family == "pending"`). Mitigated by classifying from `Capabilities`, never from the cached `Verdict`.

## Deferred (to later M8 phases)

- Per-engine-version arch-support list + VRAM/RAM fit pre-check (the authoritative `loadable`/`fits` verdict dimensions and clean fail-fast) — **Phase 3**.
- Unknown-family **warn-and-serve** default + `--require-verified` opt-out + the one-file-PR contribution pointer and contributor docs — **Phase 4**.
- The conformance G-group auto-configuring a catalog-less known-family model and running the agent tool-use/streaming gates against it; public docs + launch-post "bring your own" update — **Phase 5**.
- Inspecting/auto-configuring a **local safetensors directory** (rare; stays bare passthrough in Phase 2).
- Broadening the family map beyond the seed set (more families, gemma/llama vLLM/SGLang parser cells) — ordinary conformance-gated PRs per ADR-0015 Decision 2.

## P8.2 review — deferred findings (2026-06-28)

High-effort review of #121/#122/#123 confirmed two issues that shipped as a phase-fixes PR (canonical `--quant` token resolution — case-normalizing and rejecting ambiguous/absent requests instead of forwarding the raw string to llama.cpp's `-hf` tag; and a clearer "no selectable quantizations" error for a non-repo `--quant` target). The rest were judged non-blocking and are parked:

- **`--engine-arg` vs auto-config precedence.** Auto-config `engine_args` are appended _after_ the user's `--engine-arg` (`models.go` `start`), so for argparse-style engines (vLLM/SGLang) the auto-config value wins a duplicated flag — a user can't override an auto-configured `--tool-call-parser` via `--engine-arg`. This is **consistent with the catalog path**, which also appends its `engine_args` after the user's, so it is not a P8.2 regression. Revisit only if explicit user override is wanted; a proper fix is flag-aware dedup/last-wins ordering, which is absent for catalog models too.
- **Quant-selection layer.** `applyQuant`/`quantToken`/`resolveQuant`/`quantRE` live in `internal/cli/resolve.go`, split from the GGUF quant knowledge (`pickQuant`, `Capabilities.Files`/`Selected`) in `internal/modelmeta`. Consider moving serve-time quant selection into `modelmeta` so `inspect` and `up` share one implementation and cannot drift on the default-quant heuristic or filename conventions.
- **`parsersLine` vs `parserNote` duplication.** The family→parser-flags rendering exists in both `inspect.go` (`parsersLine`, for the `inspect` preview) and `resolve.go` (`parserNote`/inline `Classify`+`EngineArgs`, for the `up` auto-config note); extract a shared helper so the two surfaces can't diverge.
- **In-process metadata memo.** `inspectForResolve` re-reads and re-parses the on-disk inspect cache per spec, so a repeated `--model` value in one `up`/`run` invocation does redundant disk I/O. Minor; add a process-lifetime `map[spec]Capabilities` if it ever matters.
